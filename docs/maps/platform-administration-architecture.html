Administering a Fabric platform

Who may create a workspace, who changes access, and what notices when the answer is “nobody”. The design for launching a Microsoft Fabric estate and running it afterwards.

01

The shape, in one sentence

Existence is centralised, operation is delegated: the platform creates workspaces and their groups, a named human runs each one, and anything that escapes that becomes a failing check rather than a quarterly discovery.

Fabric gives you four workspace roles and a delegation primitive (domains) that does not delegate access — “domain assignment doesn’t affect item visibility or accessibility”. So delegated administration has to be assembled from the three things that do carry authority: group ownership in Entra, the workspace Admin role, and the tenant settings that gate creation. Everything below follows from that.

Terraform

Owns existence

Resource group, capacity, workspaces, capacity assignment, role assignments, the dev Git binding. Anything that must exist before content lands, and must not be recreated by a deploy.

Pipeline

Owns definitions

Item definitions and warehouse schema, per environment, from a pinned commit. It never grants access and never creates a container.

Human

Owns relationships

Groups and membership, credentials, connections and bindings, labels, item sharing, money settings, and the prod approval. Credential-shaped or judgement-shaped work.

The one-line test

Before promising automation, ask four questions: does a write operation exist, does it accept a definition, will it accept a service principal, and is it out of preview? All four, or it is manual. An endpoint existing is necessary and never sufficient.

Where the controls live

Each layer is owned by exactly one mechanism. The right column is the reason the layer cannot move.

The launch order is not negotiable

Two hard dependencies decide the sequence: a capacity must exist before a workspace can be assigned to it, and a workspace must exist before items land. Everything else can move; these cannot.

Two steps are other people’s, and they block everything

A Privileged Role Administrator must consent to the Microsoft Graph app roles — Application Administrator and Cloud Application Administrator are explicitly excluded. A Project Collection Administrator must add the first principal to the ADO organisation. Request both before the build starts, not on the morning of.

03

Groups and roles: two tiers, one naming scheme

ADR 0006 spends one Entra group per workspace on access. ADR 0010 adds a second tier for the people who run the platform itself, and the rule that keeps them apart: a platform group never holds a workspace role, and a workspace group never holds Admin.

The group catalogue
TierName patternHoldsOwner
Workspace fabric-<domain>-<project>-<env>-contributors Contributor on that one workspace the workspace’s named Admin
Workspace fabric-<domain>-<project>-<env>-viewers Viewer on that one workspace the workspace’s named Admin
Platform fabric-role-admin-api admin API allow-list membership security reviewer
Platform fabric-role-platform-engineers ADO pipeline edit rights, Terraform state platform owner
Platform fabric-role-workspace-creators the Create workspaces tenant setting tenant admin

Naming is the cheap half; the audit boundary is the valuable half. Every workspace group starts with fabric- and ends with a role word, so one Entra search finds the estate and fabric-role- separates the platform tier from the 3N workspace groups.

What a workspace role actually gets you

Four roles, fully documented, and two rows worth reading twice: Viewer can read data through T-SQL but not through OneLake or Spark, and Contributor cannot publish an app, edit OneLake security, or connect the workspace to Git — which is why the deploy principal is Contributor and nothing more.

The role you grant is a purchase

At F64 and above, a Viewer reads Power BI content on a Fabric (Free) licence. Every other role needs Pro or PPU regardless of SKU. So adding someone to a -contributors group is a licensing decision, which is why the quarterly reconciliation has to read Entra membership rather than a Fabric report.

04

Two principals, split by what they can do

The split exists for one reason: adding a role assignment needs Member or higher, so a Contributor-only principal cannot grant access. That is the boundary. Everything else about the design follows from keeping it real.

Boundary

Deploy cannot grant

Contributor is below the line where a principal may add a role assignment. That is the point of the split, not a limitation to work around.

Boundary

Deploy cannot delete

Orphan items go to the recycle bin, because a hard delete would need workspace Admin — which the deploy principal deliberately does not hold.

Boundary

Admin cannot deploy

The admin principal runs only in the gated stage. If it appeared on every merge, the approval would guard nothing.

05

The workspace factory

One path creates a workspace, and it runs in a fixed order because the naming is the contract between two systems. The group is created first; Terraform then resolves it by name, so the plan fails loudly if the identity work has not happened.

Delegated

Membership

The group owner adds people. Onboarding is a person on Monday morning, not a platform ticket. The platform manages the assignment, never the people.

Centralised

Existence

Every workspace is a Terraform object with a group and a capacity. No self-service creation, because the invariants live in the creation path.

Named

Admin

Admin goes to a human and a named deputy. Capacity admin is the same, because the documentation describes it for users only — a group cannot hold it.

Refused by design

Self-service workspace creation — turning on Create workspaces for Everyone buys speed and deletes the model: an unmanaged workspace has no group, no role assignment and no capacity discipline, and appears in every future access report as an object nobody owns. Scope the setting to fabric-role-workspace-creators or leave it off.

Groups created by Terraform — the AzureAD provider would put Directory.ReadWrite.All on the platform principal to save one click. Group creation stays manual.

06

Seven invariants, each with something that fails

A convention without a check is a comment. Each of these is cheap to state and, with the exception of the last two, cheap to assert from an API the design already calls.

  1. One group per workspace, carrying Contributor or Viewer. Offboarding happens in Entra, and the pipeline does not need to know who works here.
  2. No group carries Admin. Assertable: the admin API returns the principal type beside workspaceRole, so “an Admin assignment whose principal is a group” is a query — not a quarterly argument.
  3. No direct per-user assignment without an unexpired exception. Break-glass is a register entry with a mandatory expiry, not a memory.
  4. The platform tier never holds a workspace role. Otherwise the security reviewer can change what they review, and the audit ends.
  5. Every workspace has a named Admin and a named deputy. Prevention: a workspace with no admin is Orphaned, and the admin API still reports it Active.
  6. Every item that matters carries a label, applied by a named process. Git does not export labels and defaults do not apply to service principals, so a deploy silently produces unlabelled items. Check, do not automate.
  7. No report counts as a control until something can be red. The freshness check is the meta-control: if the nightly job stops, everything else looks calm.
07

Steady state: four operations and three assertions

Deliberately small. Every recurring operation earns its place by producing something that changes a decision or catches a failure; anything that only produces reassurance is cut.

Recurring operations
OperationCadenceOutputOwner
Deploy on merge per merge dev, then test, then prod behind an approval; the commit SHA per stage pipeline
Drift report nightly items where deployed ≠ committed, per environment platform engineer
Access report weekly principals per workspace with groups expanded, orphans flagged, blind spots stated security reviewer
Capacity review weekly utilisation, throttling, overage headroom, alert-listener health capacity owner

The assertions that turn a report into a control

What must be able to fail
CheckFails whenSource
Group-Admin any Admin role assignment’s principal is a group /v1/admin/workspaces/{id}/users
Exception a direct assignment or share has no unexpired register entry repo file ∪ admin API
Settings drift a named tenant setting differs from the committed expectation admin API, where readable
Orphan / no-capacity a workspace has no admin, or sits on no capacity /v1/admin/workspaces
Freshness any check above has not produced a report in 36 hours the job, not Fabric
Two traps that make a report lie

Role changes land at the member’s next Fabric sign-in, so a removal verified as complete may still be live in an open session. Item-permission revocation can take up to two hours.

A drift report is a record, not a control. Every deployment converges the workspace to the repo, so drift survives only between a change and the next merge — and an item the repo does not define is not overwritten, it is deleted into the recycle bin by the standard orphan call.

08

Break-glass is an expiring entry

Direct per-user role assignments and item sharing are permitted only where a register entry matches. Expiry is mandatory, because “recorded exception” without a date decays into “permanent Contributor nobody remembers” — which is exactly the finding a quarterly review is supposed to produce, arriving three months late.

# docs/access-exceptions.yaml — illustrative
exceptions:
  - principal: "a.person@example.com"          # user object id preferred
    scope:     "fabric-sales-forecast-prod"
    role:      "Member"                        # Member, not Admin
    kind:      "workspace-role"                # or "item-share"
    reason:    "publish the Q3 app; group cannot publish"
    approver:  "workspace owner"
    expires:   "2027-02-01"                   # mandatory; the report fails after this

  - principal: "b.person@example.com"
    scope:     "Sales Model.SemanticModel"
    role:      "Read"
    kind:      "item-share"
    owner:     "workspace owner"              # item sharing needs a human owner
    reason:    "external audit, one report"
    approver:  "security reviewer"
    expires:   "2026-12-15"

Item sharing gets the extra field because it is the one grant path a Viewer can create, and the pipeline never sees it. Its reach is set by tenant settings rather than by roles: shareable links that grant organisation-wide access, app audiences, and publish-to-web all bypass the workspace role model entirely.

09

The side doors, and which ones the report can see

Workspace roles are the designed path. Six others grant access the pipeline never created, and two of them are invisible to every admin API. This table belongs inside the access report, not in a separate document — an incomplete answer presented as complete is worse than no answer.

Grant paths below the workspace role
PathWho can create itVisible to admin APIsRestrained by
Item sharing Admin/Member, or anyone holding Reshare yes the shareable-link setting
Workspace app / audience Admin/Member partly publish-apps settings
Publish to web users named by the setting no allow only existing embed codes
OneLake security roles workspace Admin/Member per-item only no disabling setting found
SQL GRANT / RLS sufficient rights in the item no none — enforced per item
Shortcut and identity credentials item owner / workspace Admin no per-connection

Fabric returns a role assignment whose principal is a bare Group with no members, so “who can see what” is answered by joining three sources — Fabric’s admin API, Entra group membership, and the item’s own security endpoint. No Fabric endpoint does that join for you. The admin APIs are also rate-limited to roughly 200 requests per hour, so an estate of any size needs paging and caching rather than a loop over workspaces.

Cheap day-one switches

Turn off Allow shareable links to grant access to everyone in your organisation. Set Publish to web to Allow only existing embed codes. Enable both admin API settings for the admin principal, or the access report cannot exist at all.

10

What this design does not settle

Fabric changes monthly and previews graduate, so an undated claim is a liability. These are the gaps that remain after the design, and the reason each one is honest rather than embarrassing.

Open, and what would close it
QuestionNeedsWhy it matters here
Does a service principal need a Fabric or Power BI licence? tenant or billing cost of the automation path
Can an SP hold capacity Contributor, directly or via a group? tenant the admin principal’s ability to assign workspaces
Does a group of only service principals satisfy both admin API allow-lists? tenant the hinge of the whole admin path
Does the access-details endpoint return group principals in every configuration? tenant the group-Admin assertion is built on it
What does Fabric show for an assignment whose Entra group was purged? tenant 30-day restore window, then unknown
What is the work tenant’s Create workspaces setting? portal whether the factory is the only path
Read this before treating anything above as final

Nothing on this page was observed in a tenant. Every claim is documentation-derived and carries the date it was checked; several would be settled only by performing a deployment, which this research pack will never do. Read them as “established by documentation, unverified in practice”.
